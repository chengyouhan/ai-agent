# Query — 查詢 Wiki 並綜合回答

## 概述

Query 是使用者與 wiki 互動的主要方式。根據使用者問題，Agent 搜尋相關頁面、讀取內容、綜合回答，並可選擇性地將新分析結果保存為 wiki 頁面。

**流程**：
1. 理解使用者問題
2. 搜尋 `second-brain/wiki/index.md` 找相關頁面
3. 讀取相關頁面內容
4. 綜合分析並回答
5. 展示結果，讓使用者決定是否加入 wiki

## 詳細流程

### 第一步：理解問題

**目的**：提取問題的關鍵詞和意圖

**方法**：

1. 分析問題的主題和領域
2. 識別核心概念和關鍵詞
3. 判斷問題的意圖（解釋、比較、應用、工作流程等）

**範例**：

| 問題 | 主題 | 關鍵詞 | 意圖 |
|------|------|--------|------|
| 「LLM Wiki 是什麼？」 | LLM | Wiki、架構 | 概念解釋 |
| 「Ingest 和 Query 有什麼區別？」 | 工作流程 | Ingest、Query、區別 | 對比 |
| 「怎樣設計提示詞？」 | 方法 | 提示詞、設計、步驟 | 工作流程 |

---

### 第二步：搜尋相關頁面

**目的**：從 wiki 中找出與問題相關的頁面

**方法**：

1. 讀取 `second-brain/wiki/index.md` 的完整內容
2. 根據關鍵詞掃描頁面連結和標籤
3. 評估相關度：
   - **高度相關**：直接涵蓋問題主題
   - **部分相關**：涉及相關概念
   - **低度相關**：邊緣參考
4. 排序：高度相關 → 部分相關 → 低度相關
5. 選擇最多 5 個最相關的頁面（上下文限制）

**進度反饋**：
```
搜尋中...
找到相關頁面：
1. [[LLM-Wiki-Karpathy-摘要]] — 高度相關
2. [[Wiki 架構]] — 部分相關
3. [[知識管理]] — 低度相關
（選擇前 2 個最相關的頁面）
```

**限制**：
- 最多讀取 5 個頁面
- 若找不到相關頁面，提議建立新頁面

---

### 第三步：讀取相關頁面

**目的**：取得完整內容以回答問題

**方法**：

1. 逐一讀取每個相關頁面的完整內容
2. 提取重要段落和要點
3. 記錄頁面間的連結關係

**進度反饋**：
```
正在讀取頁面...
✓ 已讀 [[LLM-Wiki-Karpathy-摘要]] (1248 字)
✓ 已讀 [[Wiki 架構]] (856 字)
```

**限制**：
- 每個頁面最多讀取 2000 字
- 若超過，自動提取核心段落

---

### 第四步：綜合分析

**目的**：根據讀取的內容回答使用者問題

**方法**：

1. **組織信息**：將相關頁面的內容按邏輯組織
2. **交叉參照**：指出不同頁面間的連結關係
3. **標記衝突**：若多個來源有不同說法，標記並說明
4. **補充背景**：若需要，補充來自 wiki 之外的通用知識
5. **綜合回答**：生成最終答覆

**規則**：
- 優先使用 wiki 中的內容（有來源可追蹤）
- 必要時補充通用知識，但要標明來源
- 若 wiki 中有不同觀點，一併展示

**進度反饋**：
```
正在綜合分析...
✓ 已組織信息（來自 2 個頁面）
✓ 已標記 1 處潛在衝突
✓ 生成回答
```

---

### 第五步：展示結果

**格式**：

```
根據 wiki 的以下頁面：
- [[LLM-Wiki-Karpathy-摘要]]
- [[Wiki 架構]]

我的回答是：
[綜合回答的主體，分段清晰]

相關頁面：
- [[更多相關頁面 1]]
- [[更多相關頁面 2]]
```

---

### 第六步：選擇性保存新分析結果

**目的**：若分析結果有持久價值，選擇保存為 wiki 頁面

**方法**：

1. 評估回答中是否包含可重用的分析
2. 若是，向使用者提議：
   ```
   我的分析包含跨來源對比，這可能對 wiki 有價值。
   要我保存為新頁面嗎？
   （回「是」或「否」）
   ```
3. 若使用者同意，建立新頁面：
   - 命名：`[分析主題].md`（例如 `Ingest-vs-Query-對比.md`）
   - 狀態：`status: published`（或 `draft` 若不確定）
   - 標籤：`[分析, 綜合]`
   - 內容：組織回答內容，加入連結和參考
4. 更新 `wiki/index.md` 和 `wiki/log.md`

**重要**：不自動建立新頁面，需經使用者確認

## 邊界情況與處理

### 情況 1：找不到相關頁面

**症狀**：wiki 中沒有與問題相關的內容

**處理**：

1. 展示搜尋結果（若有部分相關的頁面）
2. 提議建立新頁面（但不自動建立）：
   ```
   我在 wiki 中未找到「[主題]」的相關頁面。
   這可能是 wiki 的空白。要我幫你建立一個新頁面框架嗎？
   ```
3. 若使用者同意，生成骨架頁面，標記 `status: draft`，待使用者補充

### 情況 2：多個來源的說法衝突

**症狀**：wiki 中的不同頁面對同一問題有相反敘述

**處理**：

1. 列出各個說法
2. 標記衝突：
   ```
   ⚠️ **衝突**：
   - 來源 A 認為 X
   - 來源 B 認為 Y
   
   可能原因：[分析]
   ```
3. 提議在 wiki 中新增「衝突標記」頁面

### 情況 3：問題範圍過廣

**症狀**：問題涉及多個主題，相關頁面超過 5 個

**處理**：

1. 提示使用者：
   ```
   此問題涉及多個主題（找到 N 個相關頁面）。
   要我聚焦在某個子主題嗎？
   ```
2. 請使用者詳細提問，以縮小範圍

### 情況 4：頁面內容不完整（status: draft）

**症狀**：相關頁面標記為草稿，內容不完整

**處理**：

1. 標註該頁面的狀態：
   ```
   ℹ️ 頁面 [[概念 X]] 仍在完善中（狀態：草稿）
   ```
2. 補充其他相關頁面的內容
3. 提議使用者可後續補充該頁面

## 回答品質標準

Query 的回答應該：

- [ ] 基於 wiki 內容（優先）或補充必要背景知識
- [ ] 清晰引用來源頁面（[[頁面名]]）
- [ ] 邏輯清晰，逐步展開
- [ ] 標記任何不確定性或衝突
- [ ] 提供相關頁面的連結，便於進一步探索
- [ ] 長度適中（通常 200-800 字）

1. Raw sources - 不可變的原始來源

3. Schema - 規範和工作流程

- 知識可以跨來源綜合
- 矛盾可以標記和追蹤
- 連結和結構可以逐步完善

## 常見問題

**Q: Query 會自動保存新分析結果嗎？**  
A: 不會。只展示結果，由使用者決定是否保存為新頁面。

**Q: Query 可以讀取 raw 資料夾中的檔案嗎？**  
A: 不可以。Query 只查詢 wiki 中的已編譯頁面。

**Q: 若問題在 wiki 中找不到答案怎麼辦？**  
A: 會提議建立新頁面（骨架），或提供通用知識補充。

**Q: 最多可以讀多少個 wiki 頁面？**  
A: 最多 5 個（上下文限制）。若相關頁面超過 5 個，優先選擇最相關的。
